# 콘텐츠 문서 관리 기준

## 목적과 적용 범위

이 문서는 `content/` 아래의 신규 문서 작성, 기존 문서 검토, 파일 이동을 위한 관리 기준입니다. 공개 제목, 관리용 파일명, 공개 URL을 분리해 독자가 읽는 제목과 저장소 관리 정보를 함께 유지합니다.

기존 문서의 이름 변경이나 이동은 이 기준만으로 수행하지 않습니다. 문서 대장에 기록하고, 링크와 URL 영향을 확인한 뒤 문서 하나씩 처리합니다.

## 콘텐츠 유형과 폴더 역할

| 유형        | 용도                                                | 경로                      |
| ----------- | --------------------------------------------------- | ------------------------- |
| 프로젝트    | 직접 수행한 프로젝트의 배경, 역할, 구현, 검증, 한계 | `content/projects/`       |
| 블로그      | 기술 설명, 회고, 트러블슈팅처럼 완결된 글           | `content/blog/`           |
| 노트        | 재사용할 개념, 도구, 명령어의 짧은 학습 기록        | `content/notes/<domain>/` |
| 템플릿·대장 | 작성 기준과 관리 기록                               | `content/templates/`      |

`content/templates/`는 Quartz 설정의 제외 경로이므로, 관리 기준과 문서 대장은 공개 페이지로 생성되지 않습니다.

## 관리 번호와 작성 순번

새 문서는 최초 초안 생성 시 유형별 관리 번호를 부여합니다.

| 유형     | ID 형식   | 예시                   |
| -------- | --------- | ---------------------- |
| 프로젝트 | `PRJ-001` | 첫 번째 신규 프로젝트  |
| 블로그   | `BLG-001` | 첫 번째 신규 블로그 글 |
| 노트     | `NTE-001` | 첫 번째 신규 노트      |

- 관리 번호는 문서의 고유 식별자이며, 제목·파일명·URL이 바뀌어도 변경하지 않습니다.
- 문서 대장에는 유형과 무관한 전체 등록 순번도 함께 기록합니다.
- 이 기준 제정 이전 문서는 원문 작성 순서를 입증할 수 없으므로 `LEG-*` 임시 ID로 등록합니다. 저장소 반입일을 원문 작성일로 바꾸어 적지 않습니다.

## 파일명, 폴더명, 날짜

신규 파일명과 폴더명은 소문자 영문 `kebab-case`를 사용합니다. 관리 번호와 최초 작성일을 끝에 포함합니다.

```text
content/projects/prj-001-fashion-mnist-cnn-20260902/
├── index.md
├── learning-curves.png
└── confusion-matrix.png

content/blog/blg-001-mysql-buffer-pool-incident-20260824.md
content/notes/database/nte-001-innodb-buffer-pool-20260824.md
```

- 파일명 끝의 `YYYYMMDD`는 최초 작성일입니다. 문서 수정 시 바꾸지 않습니다.
- `index.md`인 폴더 안내 페이지는 관리 번호를 부여하지 않습니다.

## 문서 구조와 자산 배치

- 프로젝트는 `content/projects/prj-001-project-slug-YYYYMMDD/index.md`처럼 폴더형으로 작성합니다. 프로젝트 전용 이미지, 도표, 공개 가능한 실행 산출물은 같은 폴더에 둡니다.
- 블로그와 노트는 각각 단일 Markdown 파일로 작성합니다. 파일명은 앞 절의 `BLG-*`, `NTE-*` 규칙을 따릅니다.
- 블로그·노트에 자산이 처음 필요한 경우에는 임의로 폴더형으로 전환하지 않습니다. Quartz의 상대 경로와 공개 URL을 검증한 뒤, 자산 경로 규칙을 이 문서에 먼저 추가합니다.

## Frontmatter와 공개 표기

신규 문서는 유형별 템플릿에서 다음 공통 필드를 작성합니다.

```yaml
title: "독자에게 표시할 한국어 제목"
doc_id: "PRJ-001"
date: 2026-09-02
created: 2026-09-02
modified: 2026-09-02
permalink: "/projects/fashion-mnist-cnn"
aliases: []
tags:
  - project
draft: true
```

- `title`은 페이지 제목·목록·링크 표기에 사용합니다. 파일명이나 관리 번호를 공개 제목에 붙이지 않습니다.
- `doc_id`는 관리 대장과 파일·폴더를 연결합니다.
- `date`와 `created`는 최초 작성일로 동일하게 시작합니다. `modified`는 본문을 고친 날짜로 갱신합니다.
- 실제 공개일을 최초 작성일과 구분해야 하면 `published`를 추가합니다.
- `permalink`은 파일 이동 뒤에도 유지할 공개 URL입니다.
- `aliases`에는 이전 URL 또는 이전 경로를 기록해 기존 링크를 보존합니다.
- 내부 링크는 파일명이 아닌 문서 제목을 보이도록 명시적인 링크 텍스트를 사용합니다.

## 자산과 근거 자료

- 프로젝트의 공개 이미지·도표는 해당 프로젝트 폴더에 둡니다.
- 블로그·노트 자산은 아직 별도 경로를 정하지 않았습니다. 실제 필요 사례가 생기면 경로·링크·빌드를 검증한 뒤 이 기준을 갱신합니다.
- 원본 노트북, 데이터, 실행 로그처럼 공개하지 않을 자료는 `자료/`에 두고 Git 추적에서 제외합니다.
- 글에는 공개 가능한 결과·이미지만 복사합니다. 원본 자료를 삭제하기 전 복사본·링크·빌드 결과를 확인합니다.
- 수치, 실행 결과, 출처는 글 안에서 근거와 검증 상태를 함께 적습니다.

## 작성·검토·공개 절차

1. 문서 대장에서 다음 관리 번호와 전체 등록 순번을 예약합니다.
2. 유형별 템플릿으로 초안을 만들고 `draft: true`를 유지합니다.
3. 관리 번호·최초 작성일·경로·제목을 대장에 기록합니다.
4. 근거 자료, 공개 범위, 이미지 경로, 내부 링크를 검토합니다.
5. 변경 범위에 맞는 Quartz 빌드를 실행합니다.
6. 검토가 끝난 문서만 `draft: false`로 바꾸고, 대장 상태를 공개로 변경합니다.

## 기존 문서 이전 절차

1. 현재 경로, 표시 제목, Git 최초·최종 반입일, 공개 상태를 대장에 기록합니다.
2. 원문 작성일과 실제 작성 순서를 확인할 수 없으면 `확인 필요`로 둡니다.
3. 문서 하나씩 새 ID·새 경로·`permalink`·`aliases`를 제안합니다.
4. 해당 문서의 내부 링크와 이미지 경로를 확인한 뒤 이동합니다.
5. 문서별 빌드·링크 검증 후 다음 문서로 진행합니다.

기존 문서를 날짜·번호 기준으로 일괄 이동하거나, Git 반입일을 원문 작성일처럼 표기하지 않습니다.

## 예외와 유지 보수

- YAML frontmatter가 깨진 문서는 번호를 부여하거나 공개 검증을 진행하기 전에 메타데이터부터 복구합니다.
- 새 콘텐츠 유형이 필요하면 기존 ID 체계와 충돌하지 않는 접두어를 먼저 대장에 등록합니다.
- 이 기준을 바꾸면 변경일과 이유를 문서 대장에 기록합니다.
