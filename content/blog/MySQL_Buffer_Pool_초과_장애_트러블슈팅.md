## 핵심 요약

- 110만건(440MB) 테이블에 대해 하나의 트랜잭션으로 SELECT/INSERT를 실행하다 InnoDB buffer pool이 초과되어 MySQL이 다운됐다.
- 세션 목록에서 sleep 3만초짜리 커넥션을 보고 의심했으나, `wait_timeout` 기본값(28800초)에 가까운 정상 범위라 원인에서 제외했다.
- 근본 원인은 `innodb_buffer_pool_size`가 128MB(사실상 기본값)로 방치되어 있었던 것. 서버 RAM 128GB를 확인해 64GB로 상향했다.

## 배경 또는 문제 상황

기존에 문제없이 쓰던 MySQL DB에서, 110만건(약 440MB) 규모 테이블을 대상으로 SELECT 후 INSERT하는 작업을 실행했다. 작업 도중 오류가 발생했고, DB 세션이 계속 잡힌 채 응답이 없어 확인해보니 로그에 buffer pool이 초과됐다는 내용이 남아 있었다. 결국 MySQL이 다운됐다.

- 재현 조건: 110만건/440MB 테이블에 대한 대량 SELECT + INSERT를 하나의 작업(트랜잭션)으로 실행
- 영향 범위: 해당 MySQL 인스턴스 전체 다운

## 핵심 내용 또는 해결 과정

### 원인 분석

먼저 `SHOW PROCESSLIST`로 세션 상태를 확인했다. Sleep 상태로 3만초 가까이 잡혀 있는 세션이 있어 커넥션 릭(connection leak)을 의심했다.

- 3만초는 약 8.3시간으로, MySQL `wait_timeout` 기본값인 28800초(8시간)에 근접한 값이다.
- 즉 비정상적으로 오래 방치된 세션이 아니라, timeout 직전까지 유지된 정상 범위의 커넥션이었을 가능성이 높다.
- **확인 필요**: 정확한 sleep 시간과 해당 세션이 실제로 유휴 상태였는지는 당시 로그를 다시 확인해야 판단할 수 있다. 이번 장애의 직접 원인으로는 보지 않았다.

세션 쪽에서 뚜렷한 이상이 없었으므로, 원인은 buffer pool 설정 자체로 좁혀졌다.

- `innodb_buffer_pool_size`가 128MB로 설정돼 있었다. 이는 MySQL 기본값과 동일한 값으로, 사실상 튜닝이 이뤄지지 않은 상태였다.
- 대상 테이블(440MB)이 buffer pool보다 훨씬 커서, 데이터 전체를 캐싱하지 못하고 페이지 교체가 반복됐을 것으로 추정된다.
- SELECT/INSERT가 동시에 대량으로 몰리면서 dirty page가 buffer pool을 채웠고, flush(디스크 반영) 속도가 이를 따라가지 못해 결국 buffer pool이 초과된 것으로 판단했다.
- **확인 필요**: 정확한 에러 로그 원문은 남겨두지 못했다. 다음 장애 시에는 `log_error` 변수로 로그 경로를 확인해 원문을 보존해야 한다.

### 해결 방법

서버의 물리 RAM을 확인한 결과 128GB였다. InnoDB buffer pool은 전용 DB 서버 기준 물리 RAM의 50~70% 수준으로 잡는 것이 일반적인 권장치라, RAM의 50%인 **64GB**로 상향했다.

```sql
-- 임시 적용 (재시작 시 원복됨)
SET GLOBAL innodb_buffer_pool_size = 68719476736; -- 64GB
```

`my.cnf` 설정 파일 자체가 서버에 존재하지 않아, 이번에는 `SET GLOBAL`로 런타임에만 임시 적용했다.

### 재검증

- **확인 필요**: 동일 조건(110만건 SELECT/INSERT)으로 재작업을 수행해 buffer pool 초과 없이 완료되는지 확인이 필요하다. 이 글 작성 시점에는 재검증을 진행하지 못했다.

## 주의점과 한계

- `SET GLOBAL`로 바꾼 값은 MySQL 재시작 시 원복된다. `my.cnf`(또는 `/etc/my.cnf.d/*.cnf`)에 영구 반영하거나, MySQL 8.0 이상이면 `SET PERSIST`로 재시작 후에도 유지되도록 조치해야 한다. 이 부분은 아직 처리하지 못했다.
- buffer pool을 키운 것은 증상 완화 조치이며, 근본적으로는 110만건을 하나의 트랜잭션으로 처리한 작업 방식 자체가 위험 요인이었다. 배치 단위로 나누는 방법은 별도 노트로 정리했다([[대용량_INSERT_배치_처리]] 참고).
- 정확한 에러 로그 원문을 확보하지 못해, buffer pool 초과가 InnoDB 자체 경고였는지 OS 수준(OOM killer 등)까지 개입했는지는 확정하지 못했다.
- DBA 경험이 없는 상태에서 처음 겪은 장애라, 이번 조치 기준(64GB, 50% 룰)이 이 서버의 다른 워크로드까지 고려했을 때 적정한지는 추후 재검토가 필요하다.
